### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

Landing needs a landing grant: the request's explicit permission to merge, land, ship, or merge when ready. Without one, report the verified run and its ceiling, and land nothing.

1. **Verify each PR independently before it lands.** GitHub CLI (`gh`) is the forge. On the cloud surface (`pstack: surface=cloud`), `gh pr` fails because GraphQL is blocked, so do the same operation with `gh api` REST. One verifier per PR, each briefed per the brief contract (read ${CLAUDE_PLUGIN_ROOT}/skills/poteto-mode/references/brief-contract.md) and each a cloud worker. Under local-only (asked for, or fallen back to and said once when cloud workers can't start), or under a cloud lead, each is a `poteto-reader` `Agent` on the Judgement setting with `isolation: "worktree"` whose brief names its start commit. Each runs the change the way a user would with the matching control skill (such as `control-ui` or `control-cli`, which ship with pstack; read ${CLAUDE_PLUGIN_ROOT}/skills/control-ui/SKILL.md or ${CLAUDE_PLUGIN_ROOT}/skills/control-cli/SKILL.md), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, with `gh pr merge <pr> --squash`, or in cloud `gh api -X PUT repos/{owner}/{repo}/pulls/<pr>/merge -f merge_method=squash`. A PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`gh pr view <pr> --json state,mergedAt,baseRefName`, or in cloud `gh api repos/{owner}/{repo}/pulls/<pr>`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Arm `--auto` (GitHub auto-merge) only on a PR whose verdict covers its current head, because it lands whatever head is ready. In cloud, never arm auto-merge: watch the PR per step 5 and merge it once it is ready. The first refused merge, whatever refuses it, stops that PR at merge-ready. Record the refusal text as a gate for the user's click and land nothing above it. No retry, no workaround. After a merge lands, retarget the PR whose base was the merged branch to trunk (`gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Watch the run with the queued watcher from `playbooks/babysit.md`, run through the runtime launcher (`${CLAUDE_PLUGIN_ROOT}/skills/poteto-mode/scripts/run watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`), until it reports `COMPLETE` at the ceiling. In cloud, where nothing is armed, watch the PR being landed alone with `${CLAUDE_PLUGIN_ROOT}/skills/poteto-mode/scripts/run watch-pr/watch-pr --pr <pr>`, and at `READY` merge it per step 4. Hold the watch from a background wait: run the watcher with `run_in_background: true` or under Monitor, so its exit wakes you. Exit 69 means no runtime: say so once with the install line it printed, and stop before calling a PR ready or landing it. Never watch the PR by hand in the watcher's place. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, each refused merge as a gate with its refusal text, and what the next gap needs. Then list the leftover branches the run pushed: merged heads still present, and closed or abandoned branches. Leave out open-PR heads. Follow the list with one `git push origin --delete <branch> …` line for the user to run locally. Never delete a remote branch yourself.
