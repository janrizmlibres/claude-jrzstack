### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack to review and land.** The sibling of **Autopilot-full**.

1. **Run the owner loop unchanged.** GitHub CLI (`gh`) is the forge. In cloud (`pstack: surface=cloud`), do the same operation with `gh api` REST. One owner per PR owns its change end to end: build, first push, a ready PR opened before self-proof, self-proof (gates, CI, receipts), skeptical triage of review bots (e.g. Claude Code Review, Bugbot, Copilot) and security-review bots per `../references/bugbot-triage.md`, a slop-strip (the `deslop` skill, which ships with pstack (`/deslop`); read ${CLAUDE_PLUGIN_ROOT}/skills/deslop/SKILL.md), `/no-comments` (the **no-comments** skill; read ${CLAUDE_PLUGIN_ROOT}/skills/no-comments/SKILL.md), and babysit to green per `playbooks/babysit.md`. Owners parallelize when the work is self-contained. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill (read ${CLAUDE_PLUGIN_ROOT}/skills/show-me-your-work/SKILL.md), pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Keep the trail uncommitted and return it in the report. Owners also keep the `children.tsv` of Autopilot-full step 2.

   Owners are sub-leads on `poteto-agent` on the Work setting, briefed per the brief contract (read ${CLAUDE_PLUGIN_ROOT}/skills/poteto-mode/references/brief-contract.md), each declaring its timebox when it starts. Pass `model:` `${user_config.work_model}` and `effort:` `${user_config.work_effort}`, or the setting's defaults (`opus`, `medium`) for a literal placeholder or an empty value. Place them as Autopilot-full step 2 does: cloud workers by default under a local lead, local worktrees under local-only, in-VM worktree subagents under a cloud lead. Spawn owners through the window. Keep at most 10 in flight, counting each in-session owner at its peak of 4 and each cloud or `create_session` owner as one (an in-session owner keeps at most 3 workers of its own in flight, so it never passes 4, and waits for them inside its own turn, as the brief contract's sub-lead clause says), and spawn the next as one finishes, never in blocking batches. A refused spawn is backpressure, whatever its error says about retrying: wait for one of your own in-flight workers to finish, then spawn again. Never drop an owner or a lane. With nothing of yours in flight, report `BLOCKED: concurrency cap`. An owner still running at 1.5× its declared timebox is stuck. It is `BLOCKED`: stop an in-session owner with `TaskStop`, record a cloud or `create_session` owner's session URL, and tell the operator once. One replacement owner then takes the item, starting from the stuck owner's pushed branch and decision trail. A replacement that also stalls is `BLOCKED`, and its item is parked and listed in the Reply, never dropped.
2. **Audit on a real loop.** The root runs an audit tick every hour. On the operator's go, the root arms `/loop 1h` through the Skill tool, with a prompt that first reads the poteto-mode skill at ${CLAUDE_PLUGIN_ROOT}/skills/poteto-mode/SKILL.md and then runs this tick, per Autopilot-full step 6. In cloud (`pstack: surface=cloud`), the root runs the same cadence from a background wait instead, since a pending loop won't wake a paused VM. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook at `${CLAUDE_PLUGIN_ROOT}/skills/poteto-mode/playbooks/autopilot-stack.md` and audit the operation against it. Fix drift during that tick. Probe each owner with a generic liveness or status check. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that passes its expected runtime without a side effect as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. An owner is stuck only past 1.5× its timebox, which step 1 handles with its one replacement. Probe all subagents and end the tick per Autopilot-full step 6. Verification swarms share the root's window with the owners.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. The root verifies each round per Autopilot-full step 4, with STACK-READY in place of merge-ready. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, push with `--force-with-lease` only after an `ls-remote` check, and set the PR base to the parent branch. Create it with `gh pr create --base <parent-branch>`. Retarget an existing PR with `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk.
7. **Absorb drift at the root, then re-verify what moved.** The root fetches current trunk and rebases the chain from bottom to top. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at the old SHAs. Apply the patch-id rule in `playbooks/shipping.md` at each verdict SHA. Anything that is no longer valid goes back through this playbook's step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up on GitHub, every link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it, with their own clicks or by arming merge-when-ready.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason, a parked item with its stalled owner's branch and its session URL when it has one.
