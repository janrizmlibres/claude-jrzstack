# Brief contract

Every brief a lead or sub-lead writes for a worker follows this contract, on both surfaces. Clauses 1 and 3 govern how you write the brief, clause 12 governs the worktrees you give workers, and clause 13 governs where the brief is written and how it is shared. The rest bind the worker, so carry each one into the brief, in a line of its own where the worker must act on it. A brief may add to the contract; it never loosens it.

1. **Entry and paths.** A separate-session worker's brief (a cloud worker, a `create_session` worker) opens with `/jrzstack:<skill>` as its first line. It names skills, never absolute paths: the other session's plugin root and checkout aren't yours. A same-session subagent may get paths with `${CLAUDE_PLUGIN_ROOT}` already substituted.
2. **Never ask the human.** No human is watching a worker, and a question stalls it for good. Return `BLOCKED` with the question and what each answer would change.
3. **The lead's voice.** Phrase the brief as your instruction to the worker, never "the user asked". The worker takes its orders from you.
4. **Own branch only.** Push only to your own branch: the `outcome_branch` your session was given, or the branch the brief designates. Never push to the base, another worker's branch or a shared branch.
5. **Start commit.** A worktree worker's brief names the commit it starts from, and its first step resets to it (`git reset --hard <sha>`), on both surfaces. The port never relies on `worktree.baseRef`, which the user's settings may point anywhere.
6. **Heavy commands.** Run every heavy command through jrzstack's machine-lock wrapper, `scripts/heavy -- <cmd>` in the jrzstack plugin, targeted to the files you own. A same-session subagent's brief gives the wrapper's substituted path; a separate-session worker takes it from its own savvy-mode reminder. Exit 75 means the lock stayed busy: that is backpressure, so do other work and re-run later. A failure already present at the start commit in a file you don't own is reported as `foreign failure: <file>`, never fixed.
7. **Missing files.** A gitignored file you need that isn't in your worktree (such as `.env`) is `BLOCKED: missing <file>`. Never create it yourself, whether by copying it from another checkout, by copying a template such as `.env.example`, or by writing it. Reading values the process environment already provides is fine.
8. **Leaf workers never fan out.** Unless the brief makes you a sub-lead, you are a leaf worker: never start a panel, swarm or arena. At a panel trigger, return `BLOCKED: needs <panel>` with what the panel needs (the artifact, the question, the evidence so far). Your lead runs it.
9. **One skill per purpose.** When a playbook names a jrzstack skill, read that skill's `SKILL.md`. Don't also invoke a same-purpose skill unless `CLAUDE.md` or the brief names it.
10. **Report.** End on a final commit on your own branch, with the report in its body (`--allow-empty` if no code changed) and exactly these trailers, added explicitly so they survive `attribution.commit: ""`; request no other trailer:

    ```
    Jrzstack-Status: PASS|ISSUES|BLOCKED
    Jrzstack-Nonce: <the nonce your brief gives>
    Claude-Session: <this session's URL>
    ```

    `Jrzstack-Nonce` is for a separate-session worker, whose brief gives it a nonce, a short random word the lead chose. Other workers leave it out. A same-session subagent also returns the report as its final message.

    How the lead reads it: a cloud worker pushes to a `claude/*` branch named from a title Claude Code generates, so the name can't be predicted and needn't carry the nonce. The lead finds the report by its trailer. From a background loop, it runs `git fetch -q origin '+refs/heads/claude/*:refs/remotes/origin/claude/*'`, then looks for the branch whose tip carries the nonce: `git for-each-ref --format='%(refname:short)' refs/remotes/origin/claude | while read -r b; do [ "$(git log -1 --format='%(trailers:key=Jrzstack-Nonce,valueonly)' "$b")" = "<nonce>" ] && echo "$b"; done`. The trailer is on the final commit only, so a match means the report is in, and the lead reads it with `git log -1 <branch>`. Judge by the loop's output: its exit code is 1 whether it found a match or not. A local worktree worker's report is read from its branch with no push, and its work is integrated by cherry-pick or merge.
11. **Sub-lead timebox and wait.** A sub-lead declares its own timebox when it starts: the sum of its plan's worker timeboxes plus its integration time. Its lead holds it to that declaration. A sub-lead that runs as an in-session subagent (not a cloud or `create_session` worker) ends its run the first time it ends its turn, so it never ends a turn with a worker in flight. Its workers still start in the background, and it waits for them inside the same turn with jrzstack's wait command, `scripts/wait-report <start-sha> <worker-branch> [<timeout-seconds>]` in the jrzstack plugin, run from its own worktree as one plain Bash command. The sub-lead's brief gives the command's substituted path. It blocks until the worker's report commit lands past its start commit and prints the report's `Jrzstack-Status`. Exit 75 means no report yet after the timeout (300 seconds by default, under the Bash timeout): re-run it. Never write your own git poll loop: a worktree-isolated agent's guard refuses git in a loop or a command substitution. A Claude Code worktree's branch is `worktree-agent-<agent id>`. Stop polling a worker at its timebox and `TaskStop` it. Integrate each result as it lands, refill the window, and hand back only when no worker is in flight.
12. **The lead's worktrees.** On either surface, before the first worktree you give a worker (an `Agent` with `isolation: "worktree"`), add `.claude/worktrees/` to the exclude file `git rev-parse --git-path info/exclude` names by running jrzstack's `scripts/exclude-worktrees` in the jrzstack plugin, as one plain command with its substituted path. It adds the line once and never twice. A sub-lead's brief gives the substituted path. Remove each worker's worktree once its result is integrated or discarded (`git worktree remove <path>`), and keep its branch. A sub-lead does the same for its own workers.
13. **Writing and publishing a brief.** Write each brief with the Write tool to a literal path in the store's `briefs/`, such as `.claude/jrzstack/orchestrate/<program-slug>/briefs/<name>.md`, and record that path as the unit's brief. A lead with no Orchestrate store makes one first with `orch init`. To share a brief on the remote, publish it with `orch brief publish <name>.md`, which commits it to the store branch, or add `--branch jrzstack/plan/<slug>` to put it beside the plan. Run it through jrzstack's runtime launcher, `scripts/run` in savvy-mode's skill directory, from the checkout's root: `<launcher> orch/orch.ts --store .claude/jrzstack/orchestrate/<program-slug> brief publish <name>.md`, as one plain command with the launcher's substituted path, so every argument is literal. It commits through a temporary index and `commit-tree` and pushes a fast-forward, never a force push. A rejected push means the branch moved: publish again. Never build a write path or a git chain for a brief from shell variables or `$(…)`, such as a heredoc into `$S/<name>.md` or a `hash-object`, `mktree` and `commit-tree` chain. Auto mode can't check such a command before it runs, so it stops on a permission prompt.
