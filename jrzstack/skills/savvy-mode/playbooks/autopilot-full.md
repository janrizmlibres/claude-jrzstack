### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your swarm, which never wrote the code, has proven the code that lands.**

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The patch-id rule in `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** The operator's grant is the run's landing grant, and without one every PR stops at merge-ready. The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** GitHub CLI (`gh`) is the forge. In cloud (`jrzstack: surface=cloud`), do the same operation with `gh api` REST. Each owner builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact, babysits to green per `playbooks/babysit.md`, and merges once steps 4 and 5 clear it.

   Open the PR early so CI and bots run alongside the work. The code is ready only after the slop-strip (the `deslop` skill, which ships with jrzstack (`/deslop`); read ${CLAUDE_PLUGIN_ROOT}/skills/deslop/SKILL.md) and the `/no-comments` pass (read ${CLAUDE_PLUGIN_ROOT}/skills/no-comments/SKILL.md), so the full swarm runs on finished code. Then rebase onto current trunk and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head, and merge-ready once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts or breaks CI, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier.

   Assume the VM dies. Soon after starting, push and start a decision trail per the **show-me-your-work** skill (read ${CLAUDE_PLUGIN_ROOT}/skills/show-me-your-work/SKILL.md), then push after every unit worth keeping. Carry the trail's new rows in the body of each pushed commit (an empty commit is fine), so a replacement reads the trail from the branch's log and the squash merge, which takes the PR body, never lands it. Whoever spawns a subagent records its id, state, and a stuck-after runtime from past runs of its kind in that trail, so the root can probe it if the parent dies. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to the root.

   **Where owners run.** Every owner is a sub-lead on `savvy-agent` on the Work setting, briefed per the brief contract (read ${CLAUDE_PLUGIN_ROOT}/skills/savvy-mode/references/brief-contract.md). It runs its own panels, briefs its own workers, and declares its timebox when it starts. Pass `model:` `${user_config.work_model}` and `effort:` `${user_config.work_effort}`, or the setting's defaults (`opus`, `medium`) for a literal placeholder or an empty value. Place each owner by the reminder's `jrzstack: surface=` line.
   - **Local lead, by default.** The owner is a cloud worker. Push the run's base first, because a cloud session sees only what is on GitHub. Start the owner under a pseudo-terminal with its brief file as the prompt: `script -q /dev/null claude --permission-mode auto --cloud "$(cat <brief.md>)"` on macOS, `script -qec "claude --permission-mode auto --cloud \"\$(cat <brief.md>)\"" /dev/null` on Linux. When the run names a cloud environment, add `--settings '{"remote":{"defaultEnvironmentId":"<env_ id>"}}'`. Read its reports only from what it pushes. An owner whose work needs the user's machine runs locally, as under local-only.
   - **Local-only.** When the operator asks for it ("local only", "no cloud workers"), or when cloud workers can't start (no Auto on the account, no default cloud environment, a failed launch), say so once and run every owner locally, in parallel. Each owner is an `Agent` with `isolation: "worktree"` and `run_in_background: true` whose brief names the commit it starts from. Its own workers get worktrees beside its own. Remove an owner's worktree once its PR merges or is abandoned, and keep the branch.
   - **Cloud lead.** Each owner is an in-VM `Agent` with `isolation: "worktree"` and `run_in_background: true` whose brief names the commit it starts from. A lead that can call `create_session` (in practice, one in Auto) gives an owner that needs a whole machine a `create_session` worker instead: push the base first, give each an `outcome_branch`, and poll `get_session` on `status_bucket`. A lead without the tool says once that Auto would allow separate-VM workers and carries on in-VM.

   Spawn owners through the window. Keep at most 10 in flight, counting each in-session owner at its peak of 4 and each cloud or `create_session` owner as one (an in-session owner keeps at most 3 workers of its own in flight, so it never passes 4, and waits for them inside its own turn, as the brief contract's sub-lead clause says), and spawn the next as one finishes, never in blocking batches. A refused spawn is backpressure, whatever its error says about retrying: wait for one of your own in-flight workers to finish, then spawn again. Never drop an owner or a lane. With nothing of yours in flight, report `BLOCKED: concurrency cap`. Hold each owner to the timebox it declared. An owner still running at 1.5× its declared timebox is stuck. It is `BLOCKED`: stop an in-session owner with `TaskStop`, record a cloud or `create_session` owner's session URL, and tell the operator once. One replacement owner then takes the item, starting from the stuck owner's pushed branch and decision trail. A replacement that also stalls is `BLOCKED`, and its item is parked and listed in the Reply, never dropped.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head. Fan out independent verifiers at the code-ready SHA per the **swarm** skill (read ${CLAUDE_PLUGIN_ROOT}/skills/swarm/SKILL.md). The swarm's workers share your window with the owners. They re-run the gates, prove the load-bearing behavior live on the real surface through its control skill (such as `control-ui` or `control-cli`, which ship with jrzstack; read ${CLAUDE_PLUGIN_ROOT}/skills/control-ui/SKILL.md or ${CLAUDE_PLUGIN_ROOT}/skills/control-cli/SKILL.md) or a named driver, and audit the diff. The verdict is not clean without the live lane, or before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked.

   Send every proven finding, whatever a lane labeled it, to the owner in one fix-forward, with a red test across every site with the same defect. A defect trunk shows without the PR is recorded against trunk and does not gate the PR, but one the PR copies or newly reaches is the PR's own. Never push a fix yourself, because each branch has one writer. Replace a stuck owner instead, per step 2.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. Once the swarm's lanes have started, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed (a path in `git diff --name-only HEAD...origin/main` that the PR also changes), or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work.

   The owner squash-merges its own PR with `gh pr merge <pr> --squash`, or in cloud (`jrzstack: surface=cloud`) with `gh api -X PUT repos/{owner}/{repo}/pulls/<n>/merge -f merge_method=squash`. The first refused merge stops that PR at merge-ready, with the refusal recorded as a gate: no retry, no workaround.
6. **Run the root layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, arm `/loop 1h` through the Skill tool to audit until no delegated work is left, because long runs drift and agents stall silently. Its prompt first reads the savvy-mode skill at ${CLAUDE_PLUGIN_ROOT}/skills/savvy-mode/SKILL.md and then runs the tick. In cloud (`jrzstack: surface=cloud`), run the same cadence from a background wait instead, since a pending loop won't wake a paused VM. Each tick re-reads this playbook at `${CLAUDE_PLUGIN_ROOT}/skills/savvy-mode/playbooks/autopilot-full.md` and fixes drift, such as an unreported head or an unrecorded agent, by having its owner record it, because drift is a gap in the record, not a stall. It probes every agent, down to the leaf lanes, and judges each by its side effects, because status text and summaries can hide a stuck child. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime, and so is an owner past 1.5× its timebox or one that has neither pushed nor written a trail row by the first tick. One waiting on you or the operator is not stuck, so answer it. Replace a stuck agent at once, without waiting for its stop to land. A stuck owner gets the one replacement step 2 describes, and a replacement that also stalls is `BLOCKED`, its item parked and listed in the Reply. A tick that changed something for the operator ends by catching them up per the **ketchup** skill (read ${CLAUDE_PLUGIN_ROOT}/skills/ketchup/SKILL.md), and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Reply:** catch the operator up per the **ketchup** skill (read ${CLAUDE_PLUGIN_ROOT}/skills/ketchup/SKILL.md), covering each PR's state and verdict, what merged, countersigns and why, and open operator gates, refused merges included, with links to each PR and the trails. List parked items, each with its stalled owner's branch and its session URL when it has one. Then list the leftover branches the run pushed (merged heads still present, closed or abandoned owner branches, open-PR heads left out), with one `git push origin --delete <branch> …` line for the operator to run locally. No lead deletes a remote branch.
